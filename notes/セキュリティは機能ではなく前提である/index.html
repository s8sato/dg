    セキュリティは機能ではなく前提である

    セキュリティは一度考えて終わるものではない。警戒と定期的な注意を要する継続的な過程である。開発工程の最初から組み込むものであって、最後に外付けするものではない。

    自分で作らない

    第一の、そして最も重要な規則がある。いかなる状況でも、自分で安全機構を作らない。

    認証の仕組みを自作するのは簡単そうに見える。だが安全の専門家は、必ずしも自明でない複雑な脆弱性を特定し緩和することに何十年も費やしてきた。実績のあるライブラリは、その年月をそのまま含んでいる。

    葉書か封書か

    手元での開発では HTTP が単に便利なので使いたくなる。だが本番に出す前に HTTPS で試すことが重要だ。手元の開発向けに信頼された証明書を作る道具はある。

    旅先から送る葉書を思えばいい。裏に書いた手書きの文面は誰にでも見える。HTTP はこれと同じで、平文を運ぶ。パスワード、カード番号、秘密、個人情報が、通信を傍受した誰にでも見える。

    私信にしたいなら封書に入れる。HTTPS がやっているのはこれで、TLS による暗号化の層を加える。TLS 証明書は Web サイトにとっての身分証で、信頼された認証局が所有者の身元を確認したうえで発行する。

    HTTPS はすべての安全問題を解決しない。 層の一つにすぎない。ログイン画面だけでなくどこでも使う。HTTP は自動的に HTTPS へ転送する。証明書は最新に保つ。安全な TLS の版（1.2 以上）を使う。

    認証は層で守る

    認証は利用者が名乗るとおりの人物かを確かめる過程であり、認可は確認された利用者が何をしてよいかを決める。両者は別物である。

    パスワードでは、漏洩済みのデータベースと照合し、使い回しを防ぎ、一つ一つに固有のソルトを付けた現代的なハッシュを使う。ソルトとはハッシュの前に加える無作為のデータで、事前計算表による攻撃を防ぐ。

    ただしどれだけ技術的な保護を積んでも、パスワードは最終的に人間の行動に依存する。付箋に書かれたり共有されたりすれば、最強の方針も役に立たない。だからこそ層を重ねる。

    失敗した試行には指数的な待ち時間を設ける。同一 IP からの複数アカウントへの試行を追い、新しい端末からの試行を利用者に知らせる。セッションでは暗号学的に安全なトークンを使い、無操作と絶対時間の両方で期限を設ける。多要素認証では複数の方式を支えるが、SMS とメールは SIM 乗っ取りのような攻撃に弱いことは知っておく。

    データは預かりものである

    利用者は自分のデータを預けている。その信頼を守ることは、職業上の責任であり倫理上の責任でもある。 開発者としての判断は、人の生活、経済的な安全、身体の安全に現実に影響しうる。

    個人を識別しうる情報（PII）には、氏名や社会保障番号のような明白なものだけでなく、IP アドレスや端末識別子のような目立たないものも含まれる。他のデータと組み合わさったときに初めて PII になるものもある。

    機微なデータを平文で保存してはならない。暗号化は安全網であり、金庫のようなものだ。破られても、鍵がなければ中身は使えない。

    適合性の実践としては、最初から privacy by design（設計段階からデータ保護を組み込む）、安全なコーディング規約、移動中と保存時の両方の暗号化、データの削除と書き出しの明確な仕組み、機微な情報とのやりとりの記録がある。

    規制をすべて暗記する必要はない。規制されたデータに自分のコードが触れたときにそれと気づき、助けを求めればよい。 安全はチームの仕事である。自分では危険に近づいていることに気づけないことがあり、それは普通のことだ。

    効く条件

    • 認証や暗号を実装しようとしたとき。まず既存の実績ある実装を探す
    • 個人情報を扱う機能に着手するとき。設計段階でしか組み込めない
    • 手元で HTTP を使い続けているとき。本番との差が、そのまま事故の種になる

    効かない条件

    ここから先は本書が書いていない領域で、読み手として当て込んだ限界である。

    • 既存システムへの後付け。正しいが、段階的な計画と優先順位付けが別途要る
    • 安全と使いやすさが対立する場面。完全に安全なシステムは使えないシステムでもある
    • 専門家が組織にいない場合。「助けを求める」相手がいなければ、外部の監査を買うしかない
