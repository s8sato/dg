    予測を先に書いて専門性と熟達と自己効力感を育てる

    答えを見る前に「どうなるか」を賭け、答え合わせをする。短い賭けで熟達を、長い賭けで専門性を、的中の記録で自己効力感を育てる。 「何が良いか」を先に書く実践と対になる（AIに聞く前に自分の見込みを書く）。

    基本動作：賭け

    学習行為の直前に、1行で賭ける。

    [賭け] 〜はこうなる / 確信度 70% / 根拠: 〜
[結果] 当たり・外れ / 差分: 〜
    • AIに質問する前: 答えはたぶんこうだ
    • コードやテストを実行する前: ここで落ちる
    • 本や論文を読む前: 結論はこうだろう

    外れの差分が学習材料になり、当たりの記録が自己効力感の根拠になる。期待を先に書いてから実行する点は、TDD と同じ形をしている（仮説思考とTDD（テスト駆動開発））。

    長い賭けで判断を鍛える

    反復で熟達は進むが、専門性はそれだけでは育たない。専門性の段差は知識量ではなく、結果を引き受ける判断の射程にある（ソフトウェアエンジニアは作る人ではなく判断に責任を持つ人である）。 数週間〜数か月後に結果が出る判断（設計、見積もり、技術選定）にも賭け、期日に精算する。判断力はここでしか鍛えられない。

    [賭け 2026-12-31] このキャッシュ層は3か月以内に外すことになる 60% / 根拠: 更新頻度が読みより高い

    賭け帳で伸びを測る

    賭けを領域ごとに蓄積し、定期的に集計する。

    指標 見るもの 使い道
    的中率 領域ごとの当たりの割合 次の課題の難度を決める
    較正 確信度70%の賭けが実際に7割当たっているか 過信・過小評価を直す
    伸び 同じ種類の賭けの的中率の推移 自己効力感の根拠にする

    較正は熟練者にも要る。Paul Graham ですら Java の成功を外した（何を学ばないかを決める）。直観の確信度は記録で割り引く。

    自己効力感を気分ではなく自分のデータに置く。AIとの共同成果では膨らみも萎みもしない、較正された効力感になる。

    的中率 50〜70% の縁で練習する

    • 80% を超える: 課題を一段上げる。熟達済みの領域に留まっている
    • 40% を下回る: 範囲を狭める。外れの原因が見えなくなっている
    • 50〜70%: 伸びる帯

    課題はAIに作らせてよい。「この概念で、自分の予測が割れそうな問題を5つ」と頼む。

    運用の候補

    以下は決定ではなく、選ぶための例示である。★は最初に試す推奨。

    賭け帳の置き場所

    候補 利点 欠点
    ★ 作業中のメモに直接書く 書く場所を探さないので続く 集計には拾い出しが要る
    領域ごとの専用ファイル 集計しやすい 開く手間で記録が途切れやすい
    CLI などでツール化 入力も集計も最速 作る前に習慣が定着していない

    まず作業中のメモに [賭け] の接頭辞で書き、週次の振り返りで grep して集める。続いてから専用化を考える。

    賭けの書式

    最小形（★）:

    [賭け] build は型エラーで落ちる 70%
[結果] 外れ / 落ちたのはリンタ。型は通っていた

    根拠は省いてよい。記録の手間が続くかどうかを決めるので、確信度だけは残す。
