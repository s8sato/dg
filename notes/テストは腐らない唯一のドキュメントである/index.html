    テストは腐らない唯一のドキュメントである

    文書は古びる。テストは古びない。継続的インテグレーションを通すために動き続けねばならないからだ。

    how と supposed to の違い

    コードは何かがどう動くかを教える。テストはどう動くべきかを教える。だから未知のコードベースでは、実装より先にテストを読むとよい。何をするはずかを掴んでから、実際にどうやっているかに降りる。

    一定額を超える注文に1割の大口割引が適用されることを確かめるテストがあれば、そこには「割引が顧客種別ではなく注文規模で決まる」という仕様が書かれている。

    @Test
public void shouldApplyBulkDiscountForLargeOrders() {
    Customer regularCustomer = new Customer(CustomerType.REGULAR);
    Order bulkOrder = new Order(regularCustomer, 500.00);
    double finalPrice = pricingService.calculateFinalPrice(bulkOrder);
    assertEquals(450.00, finalPrice, 0.01);
}

    三つの読み方

    業務プロセスを読む。 テストはしばしばユーザーストーリーに対応する。結合テストまで視野を広げれば、コンポーネントが協調して要件を満たす全体像が見える。始点から終点までを検証するテストの準備コードは、本番でシステムがどう振る舞うかの文脈をくれる。

    境界を読む。 エッジケースとは、入力や動作条件の極端な縁で想定が崩れる場所だ。shouldHandleEmptyList、shouldRejectInvalidInput、shouldTimeoutAfterTenSeconds といった名前には特に注意を払う。システムの能力の限界と破綻の地点を示している。有効期限切れのカードが穏当に拒否されることを確かめるテストは、実装を読むだけでは気づきにくい振る舞いを一行で教える。

    実行可能な文書として書く。 文書とコードの乖離は宿命ではない。テストを文書として読めるかどうかは、テストを文書として書いたかどうかで決まる。

    数字は嘘をつく

    リリースのたびに退行が出るプロジェクトがあった。テストの有無を尋ねられたテックリードは誇らしげに答えた。カバレッジは92%ある、と。

    テストコードを見ると奇妙なパターンがあり、それはコードベース全体に蔓延していた。テックリードのもとへ戻って告げる──テストにアサーションが一つもない。返ってきたのは、カバレッジの数字の繰り返しだった。

    教訓は二重だ。指標は誤誘導しうる。そして、実践の価値と目的を見失うな。儀式でしかないなら、期待した効用は得られない。

    効く条件

    • 未知のコードベースに入ったとき。テストは 未知のコードは履歴と実行から読む 際の最良の入口の一つになる
    • 仕様書が存在しない、または古いプロジェクト。テストが唯一の生きた仕様である可能性が高い
    • 実装が複雑で意図が読み取れないとき。「どう動くべきか」を先に得れば読解の負荷が下がる

    効かない条件

    ここから先は本書が書いていない領域で、読み手として当て込んだ限界である。

    • テストが実装の写像でしかない場合。実装を見ながら書かれたテストは仕様ではなく現状を固定しており、読んでも「べき」は出てこない
    • アサーションのないテスト、モックの検証しかしないテスト。カバレッジは上がるが仕様は記述されていない
    • テスト名が内容を語らない場合。名前が仕様の見出しである以上、名前が死んでいれば文書としても死んでいる
    • 網羅的なパラメータ化テスト。機械的な組み合わせの列挙は、意図ではなく入力空間を記述している
