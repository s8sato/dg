    テストの配分はピラミッドではなく文脈で決める

    Mike Cohn のテストピラミッドは、三種類のテストをどの割合で持つべきかの視覚的な指針を与える。だが実際の本数は、複雑さ・技術スタック・アプリケーションの重要度によって変わる。

    三層とその代償

    ピラミッドの構造は、テストにおける根本的なトレードオフに基づいている。上に行くほど遅く、維持が高くつき、壊れやすくなる。

    単体テストは土台であり最大の部分を占める。個々の部品を隔離して調べる、コードが果たすべき契約だ。機能的な変更があれば落ちて問題を知らせる。速く、落ちたときは特定の関数や行を指すのでデバッグが素直になる。

    結合テストは、個別にテストされた部品を組み合わせたときにだけ現れる問題を捕まえる。単体より遅く、落ちたときはどの相互作用が原因かを突き止める調査が要る。

    E2E テストは UI からバックエンドまで全体を覆い、実際の利用シナリオを模す。遅く、資源を食い、脆い。UI 要素の些細な変更で落ちることがあり、偽陰性に弱い。それでも、全体が滞りなく噛み合うという高い確信を与える。

    単体テストがマイクロ秒で終わるのに対し、E2E は数分かかりうる。数百、数千のテストがあれば、この差は劇的に効いてくる。

    何をテストしないか

    網羅的なテストは重要だが、何をテストしないかについても戦略的である必要がある。

    • 言語機能やフレームワークのコードをテストしない。それらの保守者の責任であって、こちらの責任ではない
    • getter、setter、ビルダー、自動生成された DTO のような生成コードをテストしない
    • private メソッドを直接テストしない。それを呼ぶ公開インタフェースに焦点を当てる
    • 外部サービスに依存するテストを書かない。単体ではモック、結合ではテストダブルを使う

    モックは隔離の道具である

    モックとは、依存の模造品を作ってコードを隔離して試す技法だ。アヒルのように見えて鳴くが、アヒルではない。データベースへの永続化のような実際の業務ロジックは行わず、こちらが指示したとおりに振る舞う。

    UserRepository と EmailService に依存する UserService を考える。両方を本物のまま使えば、それはもう単体テストではない。依存はそれぞれの単体テストで検証されるので、ここではモックに差し替えて UserService だけに集中する。

    裏を返せば、結合テストではこれが難しさになる。依存が協働することこそ検証したいので、複数の依存を管理し、正しい状態に保ち、相互作用を扱うことになる。いくつもの球を同時にお手玉するようなものだ。

    カバレッジは地図の明かりである

    カバレッジは、テスト実行時にコードのどれだけが実行されたかを測る。ゲームの地図に似ている。最初は全体が暗く、動き回った領域が見えるようになる。高いカバレッジは地図の大半を探索したことを、低いカバレッジはバグが潜みうる死角があることを意味する。

    80〜90%の下限を課す組織もある。善意から出ているが、逆効果を生みうる。意味のある振る舞いを検証せずにコードを実行するだけのテストを書けば、指標を出し抜ける。

    100%を目指すのは虚栄の指標になりやすい。そうではなく、自分が書いているテストへのフィードバック機構として使う。事業の中核となるロジックのカバレッジが低ければ、注意を要する領域だという合図だ。データ運搬クラスや設定のカバレッジが高ければ、不要なものをテストしている合図かもしれない。目的は任意の数字に到達することではなく、本番に出すコードへの確信を築くことである（テストは腐らない唯一のドキュメントである）。

    効く条件

    • テスト戦略を立てるとき。ピラミッドは出発点であって、規範ではない
    • E2E が増えすぎてビルドが遅いとき。同じ確信をより下の層で得られないかを問う
    • カバレッジの下限が制度化されているとき。数字ではなく、低い箇所の中身を見る

    効かない条件

    ここから先は本書が書いていない領域で、読み手として当て込んだ限界である。

    • 業務ロジックが薄く、価値の大半が結合部にあるシステム。単体テストを厚くしても守られる範囲は小さい
    • モックを過剰に使った場合。本物と乖離したモックは、通るのに本番で壊れるテストを生む
    • テストを書く人と運用する人が分かれている組織。配分の判断に必要な障害の情報が、書く側に届かない
