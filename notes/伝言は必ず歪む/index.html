    伝言は必ず歪む

    子供の頃に遊んだ伝言ゲームを思い出してほしい。言葉は人を経るたびに変わる。 同じことが組織では驚くほど頻繁に起きる。

    経路は温度で選ぶ

    意思疎通の経路は、温かいものから冷たいもの、個人的なものから非個人的なものまで幅がある。記録が残るものもあれば、後から否認できるものもある。

    聴衆も考える。メールに生きている人もいれば、何ヶ月も受信箱を見ていない人もいる。自分の世界で情報がどう流れているかを理解することが、判断の指針になる。

    メッセージは非同期であることが主たる強みだが、逆に適時に見てもらえないかもしれない。「ちょっとした質問」が人の午前中を吹き飛ばすこともある。忙しくても、質問には適時に返す。今日は手一杯だが週の後半には話せる、と言うだけでも（コードは未来の他人に宛てた手紙である）。昇進は資格だけで決まるものではなく、組織内でどう見られているかを反映する。

    保存方針がどうであれ、打ち込んだものは記録され、後から取り出されうると考える。そして書かれたものに調子は乗らない。皮肉や冗談のつもりが、文字通り真剣に受け取られうる。頭の外では違って聞こえる。

    会議は同期的で儚い。最速の解決経路になることもあるが、終わったあとも認識が揃っていないことはある。 広い配布先に送られただけで、主催者が特に自分の意見を求めていない場合もある。時間は貴重であり、出席を意図的に選ぶのは完全に妥当だ。自分は何について話すためにいるのかを尋ねると明瞭になる。

    伝言は必ず歪む

    子供の頃に遊んだ伝言ゲームを思い出してほしい。一人が右隣に囁き、それが伝わって最後の人が声に出す。言葉は人を経るたびに変わる。 発音が不明瞭だったのかもしれないし、聞いた人がそのまま繰り返さずに解釈したのかもしれない。馴染みのない言い回しを、自分の慣れたものに置き換えたのかもしれない。

    会議で誰かが言い間違え、あるいは人は聞きたいように聞く。最善の意図と相当な伝達技能があっても避けられない。だが備えることはできる。

    とりわけ社内標準のまわりで起きやすい。「Alice が、うちは標準に違反していると言っていた」「Foo が全社標準だと聞いた」。本当にそんな標準はあるのか。自分の応用に適用されるのか。証拠を持ち出すことを恐れない。

    Nate は、画面をクライアント側で描く方式の推奨実践を作ったことがある。ある部門のチームに説明しに行き、質問を受けると、一人が明らかに憤っていた。Windows MVC を使うようにアプリケーション全体を設計し直せと言うのか、なんと非常識な要求だ、と。

    驚いた。実装技術について何も言っていなかったからだ。彼らのアーキテクチャを説明してもらうと、すでに9割方その推奨実践に沿っていた。掘ると、業務側の担当者が JavaScript の MVC ライブラリに言及した発表を聞き、それが何か分からないまま Windows MVC と解釈し、標準違反を心配していたのだった。誤解が解けると、会議は極めて前向きなものになった。

    伝言ゲームに巻き込まれたら、まずそれが起きていると認識する。次にどこで言葉が歪んだかを特定する。多くの場合、どこで意思疎通が横道に逸れたかが分かれば、是正の焦点も定まる。そして誰が関わっているかを把握する。知らなかった関係者がいるなら、自分から出向いて話す。最後に、振り返りを行う。防ぐためにできたことはあったか。

    効く条件

    • 伝わっていないと感じたとき。経路の選択が間違っている可能性を先に疑う
    • 事実と異なる噂が回ってきたとき。怒る前に、どこで歪んだかを特定する
    • 記録が必要な決定をしたとき。経路には記録の有無という軸がある

    効かない条件

    ここから先は本書が書いていない領域で、読み手として当て込んだ限界である。

    • 記録が残ることが萎縮を生む文化。非同期の透明性が、率直さを犠牲にすることがある
    • 歪みの原因が善意でない場合。伝言ゲームではなく意図的な歪曲なら、是正ではなく別の対処が要る
    • 経路が組織に一つしかない場合。選ぶという前提が成り立たない
