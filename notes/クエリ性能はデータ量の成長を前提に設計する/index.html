    クエリ性能はデータ量の成長を前提に設計する

    開発環境で動くものが本番で落ちる。遅いアプリケーションは、どれだけ見た目が良くても利用者を苛立たせる。 良いクエリと悪いクエリの差は、秒からミリ秒への短縮になりうる。

    まず、取りすぎない

    書き始めのうちは、求める結果が返るクエリを書きたいだけだ。次に問うべきは「このクエリの性能をどう上げるか」である。

    SELECT * FROM users WHERE active = true

    無害に見えるが二つ問題がある。SELECT * は必要なのが一、二列でも全列を取る。 そして、数千件になりうるレコードを一度にメモリへ載せる。

    SELECT id, username, email FROM users WHERE active = true LIMIT 100

    必要な列だけを選び結果を制限するだけで、転送量は劇的に減る。常に列を明示し、大きな集合にはページングを考える。 性能が上がるだけでなく、応用が必要とするデータが何かをコードが明示することになる。

    準備済み文は二度得する

    値を文字列連結で埋め込んだクエリは、実行のたびにデータベースがまったく新しいクエリとして解析・コンパイル・最適化する。

    準備済み文（prepared statement）なら一度だけ解析・最適化し、以降は異なるパラメータでその実行計画を再利用する。頻繁に実行されるクエリで20〜50%の短縮になりうる。加えて、パラメータのエスケープを自動で扱うので、手作業の無害化なしに SQL インジェクションから守られる。

    索引と実行計画

    索引がなければ、本の中から特定の語への言及を探すのに全ページを読むことになる。索引は値と格納場所を対応づける表を作り、遅い全表走査を速い取得に変える。

    どう実行されるかを見るには EXPLAIN を使う。クエリプランナは SQL を実行計画に翻訳するコンパイラのようなもので、索引・統計・複数の実行戦略を検討する。現代のデータベースの多くは費用ベースで、複数の計画を生成して推定費用が最小のものを選ぶ。

    ページングにも落とし穴がある。オフセット方式はオフセットまでの行をすべて走査して捨てるため、大きくなるほど非効率になる。加えて総件数を数えるクエリは表の成長とともに高くつく。キーセット方式（WHERE id > last_seen_id）、件数のキャッシュや推定、総件数を要求しない無限スクロールが代替になる。

    成長は計画する

    完璧な計画はないが、計画が何もない状態は避ける。成長への備えとは、性能指標と容量を定期的に見直すことだ。クエリ応答時間が閾値を超える、CPU が恒常的に高い、メモリ使用が上がり続ける、遅いという苦情が増える。成長中のアプリケーションなら月次で、危機になる前に手を打つ。

    指標が出たときの選択肢はいくつかある。

    • 垂直スケール: サーバーに資源を足す。構成を変えずに済むので最初の一手になりやすいが、いずれハードウェアの限界に当たる
    • 読み取りレプリカ: 読み取り用の複製を作り主系の負荷を下げる。読み取りが多いなら最初に検討する。 完全な水平分散より実装が容易で効果が大きい
    • 水平スケール: 複数サーバーに分散する。垂直スケールが限界に達したとき、または地理的分散が要るとき
    • シャーディング: シャードキーで複数データベースに分割する。最も複雑だが、単一サーバーに収まらない量では必要になる

    レプリカとキャッシュは似て非なるものだ。レプリカはデータベース全体の複製で、応用側のコード変更を要さずデータベース水準の結果整合性を提供する。キャッシュは頻繁に使うデータの一時的な写しで古くなりうるため、無効化と一貫性の管理は応用側の責任になる（データストアは一貫性の要求から選ぶ）。

    効く条件

    • クエリを書いた直後。列の明示とページングは、書いたその場でしか安く入らない
    • 本番で初めて遅くなったとき。EXPLAIN が推測を事実に変える
    • 負荷の増大が見え始めたとき。読み取りレプリカが最も費用対効果の高い一手になりやすい

    効かない条件

    ここから先は本書が書いていない領域で、読み手として当て込んだ限界である。

    • データ量が小さいまま推移する場合。索引もページングも、維持費だけが残る
    • 索引を増やしすぎた場合。読みは速くなるが書きは遅くなり、容量も食う
    • ORM が生成するクエリを制御できない場合。列の明示も準備済み文も、抽象の下に隠れる
