    未知のコードは履歴と実行から読む

    未知のコードベースに向かうとき、最初に開くべきはエディタではない。人、文書、変更履歴が先に来る。

    順序がある

    まずチームメイト。次に文書──README、wiki、そしてアーキテクチャ決定記録（ADR）。ADR は、次の障害対応に追われるなかで真っ先に失われる**「なぜ」**を保存している。デバッガと数時間格闘するより、文書と数分過ごすほうが学べることは多い。ただし文書は古びている。信ぜよ、されど検証せよ。

    そして古びていたら学びながら更新し、なければ自分で作る。文書を作る行為自体が理解を助け、同時に後から来る開発者に効く（コードは未来の他人に宛てた手紙である）。重くなくてよい。何をするのか。どう動くのか。何に依存するのか。どう起動するのか。

    掘る

    エディタを開いたら考古学を始める。コードはどう組織されているか。モノリスか分散か。どんなドメイン概念が表れているか。テストは機能について何を語るか。

    意図が読めなければ、呼び出し元から逆向きに辿る。遡行はサービスの入口まで続き、やがてユーザーの操作とコードの接続が見つかる。

    見当がついたらアプリケーションを動かす。画面上の要素でもサービスの引数でも、具体的な一点をコードに対応づける。目印を探す。ある操作がデータストアの更新に至ると分かっているなら、それをコードに見つける。デバッガで歩く──予想どおりだったか、まったく違う経路に出たか。

    やっているのはメンタルモデルの構築だ。アプリケーションを脳に読み込んでいる。

    名前と例外を信じない

    コードが進化するにつれ、変数名やメソッド名は現実を映さなくなる。急がず勘を確認する。かかるだけの時間をかければ、結果的に短い時間で済む（戦略的な怠惰が生産性を生む）。

    例外も誤誘導する。非常に高いレベルの例外を捕捉している箇所には特に注意がいる。書いた側には手軽だが、起こりうる問題を覆い隠す。

    履歴を読む

    何が頻繁に変わるか。 コミットログは更新について何を語るか。最も頻繁に変更されたクラスから始めるとよい。

    git log --pretty=format: --since="1 year ago" --name-only -- "*.java" \
  | sort | uniq -c | sort -rg | head -10

    git blame は、質問すべき相手の名簿でもある。

    道具に仕事をさせる

    IDE はテキストエディタ以上のものだ。使用箇所の検索、定義へのジャンプ、呼び出し階層と依存関係図、メソッド本体の折り畳み。専用のモデル図は現実からずれていくが、コードからなら図はいつでも抽出できる。

    IDE は強力すぎて全容の把握は事実上不可能なので、週に一つ新しいことを覚えるくらいの構えがいい。

    全部は分からなくていい

    現代のコードベースは広大で、一人で全体を理解することはできないし、それは目標でもない。知識は時間をかけて増える。読む力を上げる近道はなく、読む以外にない。

    効く条件

    • 新しいコードベースに入った最初の数週間。人・文書・履歴・実行という順序が、闇雲な全文検索より速い
    • バグ修正を振られたとき。目印を一つ決めてデバッガで歩くのが最短で文脈を得る道になる
    • どこから手を付けるか決めかねているとき。変更頻度の統計が、重要な場所と不安定な場所の両方を教える

    効かない条件

    ここから先は本書が書いていない領域で、読み手として当て込んだ限界である。

    • 履歴が失われている場合。リポジトリ移行で全ファイルが一つの初期コミットに潰れていれば、手がかりは人の記憶だけになる
    • 動かせないシステム。環境の再現コストが高すぎれば「まず動かす」が成立しない
    • 探索が目的化する場合。理解の完成を待つほど変更は始まらない。曖昧さを抱えたまま小さく変え始めるほうが速いことは多い
