    ログと監視は障害が起きる前に設計する

    本番にアプリケーションを放り込んで最善を祈る開発者は多い。便りがないのは良い便りだと思っている。 実際には、利用者はおかしいと言ってこない。黙って去る。

    幸福な経路は仕事の2割

    新機能に着手するとき、幸福な経路──すべてがうまくいく理想の筋道──に焦点を当てるのは自然なことだ。だがそれは考えるべきことのごく一部でしかない。

    パレートの法則に倣えば、幸福な経路がコードの20%だとしても、境界条件と誤りの処理には80%の時間と労力がかかる。開発時間の大半はここで費やされ、経験を積んだ開発者はここで違いを見せる。

    具体的な戦略はこうなる。

    • 優雅な劣化: 機能が失敗したとき、まるごと壊れるのではなく簡素化された版を出す。天気 API が落ちているなら、古いかもしれないと断りを入れてキャッシュを見せる
    • 意味のあるエラーメッセージ: 「データベース接続に失敗しました」ではなく「いまデータを読み込めていません。数分後にもう一度お試しください」
    • デバッグのためのログ: 背後で何が起きたかを記録する。開発者に要る技術的詳細を記録し、利用者には必要なものだけを見せる
    • 代替手段: 常に第二案を持つ。主たる決済が落ちたら自動的に予備に切り替え、顧客が購入を完了できるようにする

    ログは多すぎても少なすぎても盲目にする

    ログは本番の問題への洞察を与える。難しいのは均衡である。不足すれば暗闇に置かれ、過剰なら雑音が重要な情報を覆い隠す。

    水準の概念は言語を問わず共通している。ERROR は即座の対応を要する深刻な問題、WARN は害になりうる状況、INFO は通常の業務事象、DEBUG は詳細な調査情報。

    記録してはならないものがある。

    • 機微な情報（パスワード、API 鍵、認証トークン、秘密）
    • 個人を識別しうる情報
    • 大きなオブジェクトや応答の全体。代わりに問題の特定に役立つ情報を記録する
    • 複数の層にまたがる同じ情報の重複

    二種類の監視

    実時間の監視は、いま何が起きているかを追う。応答時間は遅すぎないか。サーバーの負荷や処理量は高すぎないか。

    ただし個々の指標が全体像を語ることはない。300ミリ秒の応答は速く見えるかもしれないが、普段が50ミリ秒なら問題の兆候である。

    ログは歴史的な記録として働く。問題が起きたとき、良いログは何がいつ起きたかを再構成させてくれる。調査の文脈を与えるのはログだ。

    いくつもの重大な障害を経て定まった規則がある。

    1. 問題が起きたときに必要になる情報を記録する
    2. 常に時刻と利用者の識別子を含める
    3. 誤りは誤りとして記す。重要な警報を info に埋めない
    4. 個人情報をログの外に置く
    5. 古いログは容量を食い尽くす前に消す

    最初は単純に保つ。応答時間、誤りの件数、サーバーの資源。始めるにはそれで十分である。 凝った道具は後でよい。

    配置は旅の終わりではない

    本番に出たところが始まりである。うまく動いているときほど保守を先延ばししたくなるが、それは誤りだ。 小さく安価だった問題が、大きく高価な問題へ急速に変わる。

    OS の更新と安全修正は第一の防衛線になる。機能の更新は待てることがあるが、安全修正は速やかに当てる。

    依存関係の管理は、保守の中で最も見過ごされている側面だと言ってよい。アプリケーションは数十から数百の外部ライブラリに依存し、そのそれぞれが脆弱性を抱えうる。

    効く条件

    • 機能の実装に入る前。誤りの処理を後回しにすると、8割の作業が見積もりから抜ける
    • 本番で原因が分からない障害に遭ったとき。五つの規則が、次の障害での調査可能性を決める
    • 監視を導入するとき。三つの指標から始める判断が、道具選びの泥沼を避ける

    効かない条件

    ここから先は本書が書いていない領域で、読み手として当て込んだ限界である。

    • 異常の基準が分からない立ち上げ期。「普段は50ミリ秒」が分かるには、普段の蓄積が要る
    • ログが分散している場合。複数サービスにまたがる一つの要求は、相関 ID なしには再構成できない
    • 警報が多すぎる場合。鳴り続ける警報は、鳴らない警報と同じである
