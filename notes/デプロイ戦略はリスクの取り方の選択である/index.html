    デプロイ戦略はリスクの取り方の選択である

    本番への配置に万能の戦略はない。選んだ戦略は、円滑な展開と週末の呼び出し待機との差になりうる。

    一度に替えるか、少しずつ替えるか

    一括配置は、旧版を新版でまるごと入れ替える。実装は単純だが危険が大きい。問題があれば即座に全利用者に及ぶ。段階的な移行期がないので巻き戻しも複雑になる。小規模で利用者が限られ、停止時間を許容できる場合に向く。

    段階的配置は、一部の利用者やサーバーに先に展開してから広げる。行きつけの店が新しい品を少数の客に先に出すようなもので、反応を集め、直し、徐々に広げる。早期の問題検出と軌道修正ができる。一部の利用者に先に出すカナリア配置、サーバーを一台ずつ更新するローリング配置が代表例である。

    停止時間は、ブルーグリーン配置（同一の環境を二つ保ち切り替える）やローリング更新で最小化または解消できる。構築は複雑になるが、基幹系や高負荷のサービスには最も滑らかな体験を与える。

    どれを選ぶかは場合による。システムの複雑さ、停止への耐性、監視の能力を考える。単純に始めて、アプリケーションとチームの成熟に合わせて進化させることに恥はない。

    巻き戻しは事前にしか準備できない

    配置の自動化は、環境間でコードを動かす手作業で誤りやすい工程を取り除く。確認表を追って抜けがないことを祈る代わりに、毎回同じ信頼できる工程が走る。

    だが自動化の目的は時間の節約ではない。信頼でき再現可能な工程を作り、配置への確信を得ることにある。小さく始め、いくつかの手順を自動化する単純なスクリプトからでよい。改善のたびに危険が減る。

    巻き戻しのスクリプトを書く前に、前提がいくつか要る。

    • 配置の前に、退避された版が存在することを確認する
    • 巻き戻しの手順を定期的に試す
    • データベース移行の巻き戻し手順を文書化する
    • 複数世代の退避を保持する
    • 巻き戻しの最中もシステムを監視する

    ブランチ戦略は責務の分離である

    版管理の戦略は本番において特に重要になる。稼働中のサービスを乱さずに機能をリリースし、問題のある配置に素早く対処し、監査可能な記録を保つことを可能にする。

    • Git Flow: 複数の長命ブランチで作業の種類を分ける。開発と本番のコードを強く隔離する
    • GitHub Flow: main と短命の機能ブランチだけ。レビュー後、機能ブランチから直接本番へ
    • トランクベース開発: 全員が単一の main で働き、機能ブランチは極めて短命（しばしば一日未満）
    • リリーストレイン: 週次や月次の定期リリースに機能を束ねる

    Git Flow の補助ブランチは、それぞれ具体的な問いに答えている。

    リリースブランチは、最終試験と修正の間も次のリリース向けの機能を develop に足し続けられるようにする。版番号の更新や配置設定の変更にも専用の場所が要る。

    ホットフィックスブランチが答えるのはこの問いだ──本番に深刻な問題が出たが、develop には本番に出せない半端な機能が入っているとしたら。 安定した main から分岐すれば、不完全な機能を配置せずに直せる。修正は両方に適用され、将来のリリースで失われない。

    どの戦略でも目標は同じである。 コードを守り、作業を隔離し、変更を統合する明確な工程を作ること。

    CI/CD が全体を繋ぐ

    テストが書いた時点の確信を与えるとして、それが本番へ昇格するたびに走ることをどう保証するか。 継続的インテグレーションはチーム全体の変更を自動的に統合して試験する。継続的デリバリーは試験済みのコードをリリース可能な状態に整え、継続的デプロイはそれを本番まで運ぶ。

    効く条件

    • 初めての本番配置を設計するとき。単純に始めて進化させる方針が、過剰設計を防ぐ
    • 配置のたびに緊張しているとき。自動化と巻き戻しの演習が、緊張の実体を減らす
    • ブランチ戦略を選ぶとき。リリースの頻度と隔離の必要から逆算する

    効かない条件

    ここから先は本書が書いていない領域で、読み手として当て込んだ限界である。

    • データベースの変更を伴う配置。コードは戻せてもスキーマは戻らない。前方修正を前提に設計する（スキーマ変更は互換性を保ったまま段階的に行う）
    • 監視が貧弱な状態でのカナリア配置。一部に出しても、悪化を検知できなければ意味がない
    • 小さなチームでの Git Flow。長命ブランチの維持費が、隔離の利益を上回る
