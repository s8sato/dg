    プロンプトは文脈を与える技能である

    プロンプトエンジニアリングという語は威圧的に響くが、実体はAI と効果的に意思疎通することを学ぶだけのものだ。検索エンジンの使い方を学ぶのに似ている。専門家のために取ってある技能ではなく、誰もが育てるべきものである。

    隣の席の新人に頼むように

    隣の席の新人に「ログインのバグを直して」と頼んだとする。文脈がなければ、この単純な依頼は複雑な問題になる。課題管理システムを探し回るかもしれない。ログインのフォームは複数あるが、どれのことか。 何時間も試して、何も見つからないかもしれない。

    代わりにこう言ったらどうか。「利用者ダッシュボードのログインフォームがメール形式を正しく検証しておらず、不正なアドレスの送信を許していて、下流で問題を起こしている。」はるかに良い結果が返る。

    AI にも同じ原理が当てはまる。プロンプトの質は、応答の質に直接相関する。

    具体・構造・思考の道筋

    具体であること。 「ソート用の Java コードを書いて」は曖昧すぎる。何をソートするのか、どう並べるのか、どんなデータ構造かを指定していない。「Employee オブジェクトの ArrayList を給与の降順でソートする Java のメソッドを書いて。null 入力のエラー処理も含めて」なら、データ構造・対象・基準・順序・境界条件まで揃っている。

    構造を与えること。 良く構造化されたプロンプトは、何が欲しいかだけでなく、どう届けてほしいかを理解させる。「データベースの索引について説明して」では、深さも視点も形式も指定がない。一文で返るかもしれないし、大学院水準の説明が返るかもしれない。

    代わりに、役割（経験ある Java 開発者として）、構造（三つの部分に分けて）、長さ（各2〜3文）、具体例（PostgreSQL で索引を作る例を一つ）を指定する。

    命令ではなく教えること。 新人の良い指導者なら、特定の作業の結果をいきなり要求したりしない。できる限りの文脈を与え、既存のコードベースにある例を通じて教える。

    結果を命じる代わりに、自分の思考の道筋を辿らせる。これが思考連鎖のプロンプティングで、より正確な応答を導く。「このコードを最適化して」では、自分にとって最適化が何を意味するかの文脈がない。速度か、メモリか、可読性か。

    代わりに「大きなデータ集合を走査するこのメソッドを最適化したい。まず現在の時間計算量を特定するのを手伝って。次に具体的な改善を提案して。最後に、性能向上を説明するコメント付きでリファクタリング後のコードを見せて」と書く。作業を論理的な段に分け、目標を指定し、コードと並んで説明を求めている。

    すぐ使える工夫

    • 文脈を具体的に与える。 更地の新規案件か、現代的な実践を取り込めない既存のレガシーか。個人の制作か、業務の基幹か
    • 例を示す。 良い出力がどう見えるかを見せる。特定の書式が欲しいなら例を添える
    • 環境を伝える。 言語の版、使っているフレームワーク、抱えている制約
    • 役割を指定する。 「上級アーキテクトとしてこのコードをレビューして」。応答の詳細度と視点が定まる
    • 反復して磨く。 一度目で完璧を期待しない
    • AI にプロンプトの改善を頼む。 望む結果が出ないとき、どう言い換えるべきかを尋ねる
    • 良いプロンプトを保存する。 似た依頼は将来も必要になる

    例の与え方にも段階がある。ゼロショットは例を与えずに頼む。それで十分なこともある。ワンショットは、従ってほしい型を確立するために例を一つ与える──たとえば自分の好むコーディングスタイルのメソッドを一つ見せる。

    効く条件

    • 期待した答えが返らなかったとき。原因は多くの場合モデルではなく文脈の不足にある
    • 既存のコードベースに沿った出力が欲しいとき。規約は例で伝えるのが最も速い
    • 同じ種類の依頼を繰り返しているとき。プロンプトは資産として蓄積できる

    効かない条件

    ここから先は本書が書いていない領域で、読み手として当て込んだ限界である。

    • 自分が答えを分かっていない場合。文脈を与えられないなら、検証もできない
    • 長大な文脈を与えた場合。情報量と精度は単調には比例せず、要点が埋もれることがある
    • モデルや製品が変わった場合。特定の言い回しへの最適化は、移植性を持たない
