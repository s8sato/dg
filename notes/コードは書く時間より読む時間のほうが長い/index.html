    コードは書く時間より読む時間のほうが長い

    プログラミングの教え方は順序が逆になっている。読むより先に書くことを学ぶのに、キャリアの相当部分は他人が書いたコードを読むことに費やされる。

    白紙から始まらない

    入門講座はいきなりコードを書かせる。ポーランド語やポルトガル語を同じやり方で学ぶ人はいないのに、だ。学術的な課題はほぼ必ず白紙から始まる──以前の仕事の重荷を背負わないグリーンフィールド開発だ。

    職業生活で白紙のエディタから始める機会は驚くほど少ない。実務の大半はブラウンフィールド開発であり、既存コードベースの制約の中で日々レガシーコードと向き合う。エージェント型のプログラミングが広まるほど、自分が書いていないコードと働く量はむしろ増える。

    レガシーという語が褒め言葉として使われることはまずない。だが何年も事業価値を出し、投資の継続を正当化してきたアプリケーションを貶めるべきではない。継承コード（heritage code）という枠組みのほうが適切だ。

    四つの問題が同時にある

    既存コードにまつわる問題を解けと言われたとき、解くべき問題は四つある。

    1. 事業上の問題を理解すること。 ソフトウェアが世界を飲み込むにつれ課題は複雑化し続け、低いところの果実はあらかた摘まれた
    2. 先に来た開発者の目を通して問題を見ること。 これがしばしば最も難しい。前任者は自分の知らないスタイル、パターン、ライブラリを使ったかもしれない。賛成するかどうかとは別に、ある問題には多くの解き方がある
    3. 抽象度が適切でない可能性。 汎用に過ぎるか、ドメインの機微を捉え損ねているか。理解可能にするには大きなリファクタリングが要るかもしれない
    4. 技術的負債の層を一枚ずつ剥がすこと。 今日のベストプラクティスは明日のアンチパターンだ。コードは書かれた時点のレンズを通して見る必要がある。使われている言語機能から年代測定できることさえある

    さらにパッチの上のパッチがある。前任者が問題を理解していなかったのかもしれないし、AI アシスタントで一日2万行を生成したのかもしれない。そこに「早く直せ」が加われば、一つのメソッドの解読に午後を使う。

    自分のコードを高く見積もる二つのバイアス

    既存コードが嫌われる理由は技術的な難しさだけではない。

    IKEA 効果。自分が作ったものに高い価値を置く傾向で、ある研究では、自分で組み立てた製品に同一の完成品より63%高い額を払うという結果が出ている。ソフトウェアでは「正しいやり方」への強い意見として現れる。

    単純接触効果。馴染みのあるものを好む傾向で、言語をめぐる独断論の温床になる。Java にラムダ式が入ったとき「この新奇なラムダとやらがなぜ必要か」と問うた人がいた。ラムダが Java の当初の計画に含まれていたことを知らないまま。

    Paul Graham はこれを Blub 言語という架空の例で描いた。Blub プログラマが能力の連続体の下を見ると、日常的に使う機能を欠いた言語しか見えない。上を見ると奇妙な機能の束しか見えず、Blub になくても生産的なのだから要るはずがないと考える。

    同僚の頑なさが理解できないとき、これらを疑ってみるとよい。そして当然、自分が同じ傾向を示していないかも省みる。

    自分の古いコードに落胆してよい

    ひどいコードに毒づき、犯人が自分だったと気づく。誰にでもある経験だ。数年前のコードに少し落胆するなら、それは成長の証である。

    効く条件

    • 転職・異動の直後。コードベースの難しさを自分の能力不足と取り違えないために、四つの問題という分解が効く
    • 技術選定の議論が感情的になったとき。バイアスに名前があるだけで、議論を人格から切り離せる
    • 古いコードを「書き直すべきだ」と言いたくなったとき。それが価値を出してきた事実を先に認める

    効かない条件

    ここから先は本書が書いていない領域で、読み手として当て込んだ限界である。

    • 本当に捨てると決まったコード。読解への投資は回収されない
    • バイアスの名前を他人への攻撃に使う場合。「それは IKEA 効果ですね」は議論を終わらせる道具になりうる。自分に向けるときにだけ安全
    • 継承コードという言い換えが、変更の必要性から目を逸らす口実になる場合。敬意と現状維持は別物
